# Triage issues

Run the repository's canonical triage workflow over a fixed starting set of
issues. Use this skill for a one-shot run or for an autonomous loop. The
vendored `triage` skill remains the source for role names, brief format, notes
format, redundancy checks, prior-rejection checks, and the AI disclaimer.

## Invocation

Accept a natural-language request plus these optional controls:

- `once` runs one pass and exits after the starting set reaches a terminal
  outcome or an explicit checkpoint.
- `loop` repeats the pass with the wake mechanism from
  `patina-mode/playbooks/autonomous-run.md`. A loop must have a finite interval
  or an operator stop signal.
- `filter` limits the inbox by live tracker query, label, project, or explicit
  issue identifiers. Resolve the filter through the tracker adapter.

If the request does not name `once` or `loop`, use `once`. Never guess a
provider, label ID, status ID, or priority order from prose. Read live tracker
data through `docs/issue-tracker.md` before the run starts.

## Durable run state

Create a local, uncommitted run record before the first issue. Keep it under
`.scratch/triage-issues/runs/<run-id>.json` and keep a matching
`.scratch/triage-issues/runs/<run-id>.tsv` decision trail. Do not commit these
files, publish them, or use them as tracker state. A run record has:

```json
{
  "schemaVersion": 1,
  "mode": "once|loop",
  "filter": "the exact filter input",
  "startedAt": "ISO timestamp",
  "startingIssueIds": ["issue-123"],
  "cursor": 0,
  "issues": {
    "issue-123": {
      "snapshot": "tracker updatedAt and fields used for the decision",
      "outcome": "pending|completed|checkpoint",
      "notesCommentId": "the single AI notes comment, when present",
      "lastEvidence": ["repo path or tracker reference"]
    }
  }
}
```

The authoritative writer refuses to advance an issue unless the current live
snapshot matches the snapshot recorded for that decision. Re-read the issue
before every write. If another actor changed a field, record a checkpoint,
refresh the snapshot, and continue with that issue on the next pass. Never
reset the run record to make a rerun appear clean.

## Fix the starting set

At run start, resolve the filter and capture the complete ordered issue set.
The set is immutable for that run. Issues that arrive after the snapshot wait
for the next run. Order by live native priority, from Urgent through High,
Medium, Low, and no priority. Within each priority, process the oldest
tracker-created issue first. Do not set priority during triage unless the
evidence proves a live user-impacting fault.

For every issue in the snapshot, fetch the full issue, native relationships,
comments, labels, status, author, and timestamps through the adapter. Resolve
the category and state role labels from live label data. A missing label mapping,
unreadable relationship, or failed adapter operation is a checkpoint, not a
guess.

## Process one issue

Process issues serially in priority order. A blocked decision must not stop
independent issues.

1. Resume from the run record and prior tracker comments. Keep exactly one
   current AI-authored `Triage Notes` comment. Update that comment in place
   through the adapter. Never edit or delete a human comment. Every new or
   updated triage comment starts with:

   ```text
   > *This was generated by AI during triage.*
   ```

2. Run the vendored triage context checks. Search for an existing
   implementation by domain concept, then read every relevant
   `.out-of-scope/*.md` rejection. Record the search paths and conclusions in
   the notes.

3. Verify the claim before deciding. Use `how` for missing facts, `why` for
   rationale, and `diagnosing-bugs` for root cause. Use the target repository's
   verification skill when behavior needs proof. A bug with insufficient
   evidence stays `needs-info` with specific questions.

4. Diagnose the issue. Preserve the two category roles (`bug` and
   `enhancement`) and five state roles (`needs-triage`, `needs-info`,
   `ready-for-agent`, `ready-for-human`, and `wontfix`). Every settled issue has
   exactly one category role and one state role. Conflicting state labels
   require an operator checkpoint before any label change.

5. Apply the smallest adapter transaction that represents the evidence.
   Changes to labels, comments, status, and native relationships all go
   through the adapter and must keep any synced issue in step. Preserve every
   unrelated native field. The `triage-issues` exception in
   `docs/issue-tracker.md` permits the two native closure outcomes below.
   - `ready-for-agent` gets the canonical durable agent brief.
   - `ready-for-human` gets the same brief plus the human-only reason.
   - `needs-info` gets the canonical notes template with actionable questions.
   - `wontfix` gets a reason and native `Canceled` status when no action is
     needed or the issue no longer reproduces.
   - A duplicate gets native `Duplicate` status and a native relation to its
     canonical issue.

   Never move an issue to `Todo`. A person owns that final move. Do not close a
   `wontfix` issue without verifying native closure, or without an explicit
   checkpoint that names the failed verification.

6. Mark the issue `completed` only after one category, one state, and current
   notes or a brief are visible in live tracker data. Mark `checkpoint` when an
   operator decision, missing evidence, label mapping, relationship, or adapter
   repair is required. Continue with the next issue.

## Stop and continue rules

Stop the current issue, not the run, when evidence is incomplete or a decision
belongs to the operator. Notify the operator only for a label, relationship, or
status change, a new completion, a failed recovery, or a checkpoint that needs
action. Keep working on independent issues while a checkpoint waits.

A one-shot run exits when every starting issue is `completed` or has an explicit
`checkpoint`. A loop sleeps through the configured interval, takes a fresh
starting-set snapshot, and resumes only from durable records whose live
snapshots still match. An unchanged second run makes no tracker writes and
posts no new comment. If new evidence appears, merge it into the single notes
comment and record the changed evidence before writing.

On adapter failure, retry only safe transient failures. After the retry fails,
record the exact operation and error in the trail, notify the operator, and
continue independent issues. Never call a provider directly outside the
adapter, hide an error, or manufacture a successful outcome.

## Completion report

Report the mode, exact filter, starting issue IDs, completed outcomes,
checkpoints, adapter operations, evidence paths, and whether the rerun was a
no-op. Include the run-record path and decision-trail path. Keep both files
local and uncommitted.
